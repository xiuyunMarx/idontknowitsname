\section{Design}
We designed \sysname, a serving layer that exploits the heterogeneity of programmatically generated LLM requests to schedule the KV cache more efficiently, closing the gap between the runtime that generates prompts and the engine that serves them.

\sysname employs two planes to comprehensively discover and exploit such heterogeneity. The discovery plane first lifts each incoming prompt back to its call-site signature and bindings, then combines this metadata with request history to learn how each binding evolves and the structure of the agentic application. The scheduling plane consumes this knowledge at two levels: it reorders prompts to enlarge prefix reuse, and it places KV segments across device and host with a heterogeneity-aware eviction policy to ensure that reusable KV-cache segments reside in the correct tier.

\subsection{Discovering Heterogeneity}
\label{subsec:Discovering Heterogeneity}
\sysname first lifts each received prompt back to its call-site metadata. It then analyzes how each binding evolves across the request history along two dimensions, intra-call-site evolution and cross-call-site sharing, and assigns every binding a lifetime and sharing class. Separately, \sysname learns the application's call structure as a time-annotated probabilistic finite-state machine (TPFM). The result is a per-request record that annotates each binding with its class and future reuse estimator; the scheduling plane then consumes this knowledge.

\subsubsection{Lifting prompt back into metadata}
The lowering process is lost when prompts cross the boundary between the runtime and the serving engine. However, because prompts are lowered by the runtime through a deterministic process, these generated requests still retain recoverable structure. The runtime emits a fixed skeleton from the declaration, consisting of the header with its signature, schema rows, and output-format tail, and drops each bound argument into a slot of that skeleton, labelled by the parameter name and placed in declaration order. The skeleton then stays static and only the binding values change.

Lifting is therefore template application run backwards. We represent a call site $x$ by a prompt template $T_x=\langle S_x,(g_1,\ldots,g_m),\tau_x\rangle$, where $S_x$ is the static system prompt, $\tau_x$ is a request-only tail, and each segment is either a static byte string or a named slot:
\[
g_i ::= \textsc{Static}(b) \mid \textsc{Slot}(n,\ell),
\]
where $n$ is the parameter name and $\ell$ is its literal label. Rendering replaces every slot with its binding value, while splitting matches the static segments and labels to recover the bindings. A valid template must satisfy 
\[
\textsc{Render}(T_x,\textsc{Split}(T_x,u))=u
\]
for every observed request $u$ of the site.

The compiler may provide $T_x$ directly; otherwise, the serving engine deduces it from call history. Requests are first grouped by a call-site fingerprint consisting of the model, system prompt, and call-message header. Given at least two distinct messages from one site, the engine computes their longest common subsequence of lines. Common lines form the static skeleton and the regions between them are candidate slots. Within each region, repeated labels identify parameter names and split the region into named slots. If no reliable label pattern exists, the complete region remains one conservative slot. A suffix found only in the live request is recorded separately as the request-only tail. The metadata for a programmatically generated prompt typically includes binding names and values, the system prompt, and invariant headers, as shown in Figure~\ref{fig:heterogeneity-sample}. Such metadata is obtained by applying the template to the received prompt.

\begin{algorithm}[t]
\caption{Deducing a prompt template}
\label{alg:deduce-prompt-template}
\begin{algorithmic}[1]
\Require call history $H_x$
\Ensure $T_x$ or $\bot$
\State $(U,\tau)\gets\textsc{Normalize}(H_x)$ \Comment{extract calls and strip request-only tail for distinct messages}
\State $K\gets\textsc{LCS}(\{\textsc{Lines}(u):u\in U\})$ \Comment{find recurring lines}
\State $R\gets\textsc{Gaps}(\textsc{Align}(K,U))$ \Comment{collect changing regions}
\State $G\gets\textsc{Segment}(K,R)$ \Comment{form static segments and slots}
\State $T\gets\langle\textsc{System}(x),G,\tau\rangle$ \Comment{assemble the template}
\If{$\textsc{RoundTrip}(T,U)$} \Comment{verify exact reconstruction}
    \State \Return $T$
\EndIf
\State \Return $\bot$
\end{algorithmic}
\end{algorithm}

\subsubsection{Identifying heterogeneous evolution patterns}
Heterogeneity identification involves intra-callsite evolution patterns and cross-callsite sharing. Some components may remain static across invocations, some are shared across call sites, some accumulate as execution progresses, and some are simply transient. The identification is derived from history analysis.

\paragraph{Intra-callsite evolution}
For each binding, we compare its value across consecutive calls of the same callsite within a session. We count and record the transitions as \emph{same}, \emph{extend}, and \emph{fresh}. Concretely, \emph{same} means the binding value remains identical, \emph{extend} means the new value extends the old value by appending content to its end, and \emph{fresh} denotes a distinct value.

\paragraph{Cross-callsite sharing}
Cross-callsite sharing means a binding's value is used by multiple callsites. We check whether another callsite in the same session already carried the same value, or a prefix that the current value extends. Sharing exposes an extra opportunity to make a prefix reusable across callsites.

We characterize each binding by one of four evolution behaviors:
\begin{itemize}
\item \emph{Constant}: the same literal recurs across sessions;
\item \emph{Copied}: the binding retains or reuses a value observed earlier in the same session;
\item \emph{Extended}: the new value extends an earlier value by appending;
\item \emph{Volatile}: the binding is usually replaced by a fresh value.
\end{itemize}

For each binding name $n$ at callsite $x$, we record both its value origin and its evolution between consecutive invocations of $x$. An origin rule is considered dominant after it has been observed at least twice and accounts for at least half of the binding's observations.

A binding is \emph{Constant} when its dominant origin is a recurring literal. Otherwise, when same-callsite transitions exist, let
\[
\rho(x,n)=\frac{N_{\mathrm{fresh}}}{N_{\mathrm{same}}+N_{\mathrm{extend}}+N_{\mathrm{fresh}}}.
\]
Conceptually, the binding is \emph{Volatile} when $\rho(x,n)>\tfrac{1}{2}$; otherwise, its non-fresh behavior is \emph{Copied} or \emph{Extended}, according to whether $N_{\mathrm{same}}$ or $N_{\mathrm{extend}}$ is larger.

A callsite invoked only once per session provides no same-callsite transitions. In that case, its dominant origin determines whether the binding is copied or extended; an unresolved or other origin is treated as volatile for stability ordering.

Independently, a binding is marked \emph{cross-stable} when:
\begin{enumerate}
\item at least one observation is shared from a different callsite;
\item cross-callsite sharing accounts for at least half of its observations; and
\item either no same-callsite transitions exist or $\rho(x,n)\leq\tfrac{1}{2}$.
\end{enumerate}

We represent the ordering stability of binding $n$ at callsite $x$ by
\[
\sigma(x,n)=\bigl(c(x,n),\rho(x,n),r(x,n)\bigr),
\]
where
\[
c(x,n)=\begin{cases}0, & \text{if $(x,n)$ is cross-stable},\\1, & \text{otherwise}.\end{cases}
\]

For a constant binding, we set
\[
\bigl(\rho(x,n),r(x,n)\bigr)=(-1,0).
\]
When transition observations exist, $\rho(x,n)$ is the fresh-transition fraction, and $r(x,n)$ is the rank of the most frequent non-fresh transition:
\[
r(\mathrm{same})=1,\qquad r(\mathrm{extend})=2,
\]
with $r=3$ when no non-fresh transition has been observed.

When no transition observations exist, we set $\rho(x,n)=1$ and derive $r(x,n)$ from the dominant origin:
\[
r(\mathrm{copy})=1, r(\mathrm{extend})=2, r(\mathrm{other\ or\ unresolved})=3.
\]
Bindings are ordered lexicographically by $\sigma$, so cross-stable bindings precede other bindings, followed by increasingly volatile bindings.


\subsubsection{Deriving application-level agent TPFM}
\sysname treats agents as time-annotated probabilistic finite-state machines (TPFMs). We formulate the TPFM for agent applications as follows:
\[
\mathcal{A} = (Q, P, q_0, F, \mathcal{T}),
\]
where:
\begin{enumerate}
    \item $Q$ is the set of states. Each state $q\in Q$ is labelled by an LLM callsite; 

    \item $P$ denotes the transition probabilities between states.

    \item $q_0 \in Q$ is the entrance callsite.

    \item $F$ specifies the termination probability of the agent at each state.

    \item $\mathcal{T} = \left\{D^{\mathrm{exec}}_q,
    D^{\mathrm{gap}}_{q,q'}\right\}$ denotes the timing annotations associated with states and transitions, where
    $D^{\mathrm{exec}}_q$ is the execution-time distribution of the LLM callsite represented by state $q$, and
    $D^{\mathrm{gap}}_{q,q'}$ is the inter-call gap distribution between the completion of callsite $q$ and the invocation of its successor $q'$.
\end{enumerate}

During one session, the server observes only a sequence of LLM calls. \sysname aggregates the completed sequences into a prefix-tree acceptor whose nodes and edges retain their observed frequencies. For each application, the automaton is rebuilt whenever the number of completed sessions reaches $8\cdot 2^k$, for $k=0,1,2,\ldots$. During rebuilding, \sysname applies an Alergia-style red--blue state-merging procedure to the prefix tree, merging two states when their outcome frequencies satisfy
\[
\left|\frac{c_1}{n_1}-\frac{c_2}{n_2}\right|<\sqrt{\frac{1}{2}\ln\frac{2}{\alpha}}\left(\frac{1}{\sqrt{n_1}}+\frac{1}{\sqrt{n_2}}\right),\qquad \alpha=0.05.
\]

Here, $n_i$ is the number of observed visits to state $i$, and $c_i$ is the number of those visits that produce the particular outcome. Once two states are merged, their visit, termination, transition, and timing observations are combined to construct the resulting TPFM.

\subsection{Heterogeneity-aware KV Cache scheduling}
The discovery plane identifies where reuse exists: the ordering-stability tuple characterizes the lifetime and sharing scope of each binding, the value-flow rules identify which future binding values can be reconstructed, and the TPFM supplies call-transition and timing observations. The scheduling plane turns this information into cache actions by exposing reusable content as a prefix and placing KV cache effectively. \sysname combines prompt re-layout, future KV-demand estimation, deadline-driven promotion, and prediction-aware eviction to achieve this goal.

\begin{algorithm}[t]
\caption{Heterogeneity-aware prompt re-layout}
\label{alg:relayout}
\begin{algorithmic}[1]
\Require Callsite $x$, system prompt $S_x$, header $H_x$,
         bindings $B$, request-only tail $\tau_x$
\Ensure Re-laid-out prompt
\State $\pi_x$: layout of callsite $x$
\If{$\pi_x$ is not frozen}
    \If{any binding has insufficient observations}
        \State \Return $S_x \Vert H_x \Vert
               \textsc{Render}(B) \Vert \tau_x$
    \EndIf
    \State $\pi_x \gets \textsc{StableSort}
           (\textsc{Names}(B),\, \text{key}=\sigma(x,\cdot))$
    \State Freeze $\pi_x$
\EndIf
\State $V \gets \textsc{Render}(B, \pi_x)$
\If{$\pi_x$ is nonempty and $c(x,\pi_x(1)) = 0$}
    \State \Return $S_x \Vert V \Vert H_x \Vert \tau_x$
\Else
    \State \Return $S_x \Vert H_x \Vert V \Vert \tau_x$
\EndIf
\end{algorithmic}
\end{algorithm}

\subsubsection{Exposing reuse through prompt re-layout}
KV-cache reuse requires requests to share an identical token prefix. However, developer-defined declaration order may not account for this requirement, resulting in reduced prefix reuse. \sysname therefore revises the binding order of each callsite according to the heterogeneity learned by the discovery plane.

For every binding $n$ of callsite $x$, \sysname uses the ordering-stability tuple $\sigma(x,n)=(c(x,n),\rho(x,n),r(x,n))$ defined above. Once every binding at the callsite has accumulated enough observations, the bindings are stably sorted in lexicographic order of $\sigma$ and the resulting layout is frozen. Consequently, cross-stable bindings lead the request, constants precede session-varying values, bindings with a smaller fresh-transition ratio precede more volatile bindings, and same-valued bindings precede append-only bindings when their preceding components tie. Bindings with identical ordering-stability tuples retain their original relative order.

Ordinarily, the re-laid-out request has the logical form
\[
S_x\;\Vert\;H_x\;\Vert\;b_{\pi(1)}\;\Vert\;\cdots\;\Vert\;b_{\pi(m)}\;\Vert\;\tau_x,
\]
where $S_x$ is the system prompt, $H_x$ is the callsite-specific header and schema, $\pi$ is the learned binding order, and $\tau_x$ is the request-only tail. If the first binding is cross-stable, $H_x$ would prevent two different callsites from sharing that binding as a prefix. In this case, \sysname places the callsite-specific header after the binding values:
\[
S_x\;\Vert\;b_{\pi(1)}\;\Vert\;\cdots\;\Vert\;b_{\pi(m)}\;\Vert\;H_x\;\Vert\;\tau_x.
\]
This header-last layout exposes reuse across callsites without changing the system prompt or the binding contents. 

\subsection{Prediction-guided KV Management}
Re-layout exposes reusable prefixes in incoming requests, while proactive cache placement requires anticipating future reuse. \sysname predicts when future calls will arrive and uses binding evolution patterns to reconstruct their known prefixes, guiding fine-grained KV-cache prefetching and retention. For every live session, \sysname maintains the observed callsite history $h_t=(x_1,\ldots,x_t)$ and periodically produces a forecast
\[
\widehat{\mathcal{C}}_t=\left\{(x,p_x,t_{50,x},t_{90,x})\right\},
\]
where $x$ is a possible future callsite, $p_x$ is its cumulative reachability within the planning horizon, and $t_{50,x}$ and $t_{90,x}$ are the estimated median and pessimistic arrival times relative to the current timing anchor.

\paragraph{Single-step next-call probability estimation}
Because transition frequencies can be sparse during online learning, \sysname complements the constructed TPFM with a bounded-context predictor over callsite sequences. The predictor stores all observed callsite subsequences of length at most $K=4$ in a context trie. For a context $u$, let $C_u(x)$ be the number of times callsite $x$ follows $u$, let $C_u(\bot)$ be the number of sessions that terminate after $u$, and define
\[
\begin{aligned}
n_u &= C_u(\bot) + \sum_x C_u(x), \\
T_u &= \left|\{x : C_u(x) > 0\}\right|
      + \mathbf{1}[C_u(\bot) > 0].
\end{aligned}
\]
The confidence assigned to context $u$ is
\[
\lambda_u=\frac{n_u}{n_u+T_u}.
\]
Starting from the empty context, \sysname applies Witten--Bell-style interpolation over increasingly long observed suffixes:
\[
\widehat{P}(x\mid u)=\lambda_u\frac{C_u(x)}{n_u}+(1-\lambda_u)\widehat{P}(x\mid\operatorname{suffix}(u)),
\]
\[
\widehat{P}(\bot\mid u)=\lambda_u\frac{C_u(\bot)}{n_u}+(1-\lambda_u)\widehat{P}(\bot\mid\operatorname{suffix}(u)).
\]

A well-supported long context can dominate the prediction, whereas a sparsely observed context is interpolated with its better-supported shorter suffixes rather than being used as a deterministic prediction. The termination outcome only consumes probability mass and does not create a successor in the prediction tree.

\paragraph{Cumulative reachability and arrival time.}
A single next-call prediction is insufficient for preparing calls several steps ahead. \sysname therefore performs a bounded best-first expansion of possible future executions. We define a frontier element as
\[
(\pi,h,q,u_{50},s^2,d),
\]
where $\pi$ is the partial-path probability, $h$ is its hypothetical callsite history, $q$ is its current TPFM state, $u_{50}$ is the estimated median completion time of its last call, $s^2$ is its accumulated squared timing spread, and $d$ is its depth. The initial frontier contains $(1,h_t,q_t,0,0,0)$.

For a candidate successor $x$, the new path probability is $\pi'=\pi\widehat{P}(x\mid h)$. Let $q'$ be the state reached by $x$, and let
\[
g_{50}=Q_{0.5}\!\left(D^{\mathrm{gap}}_{q,q'}\right),\qquad g_{90}=Q_{0.9}\!\left(D^{\mathrm{gap}}_{q,q'}\right).
\]
The estimated arrival times and spread of $x$ are
\[
a_{50}=u_{50}+g_{50},\qquad s_a^2=s^2+(g_{90}-g_{50})^2,\qquad a_{90}=a_{50}+\sqrt{s_a^2}.
\]
To expand the path beyond $x$, \sysname adds the execution time of $x$. With
\[
e_{50}=Q_{0.5}\!\left(D^{\mathrm{exec}}_{q'}\right),\qquad e_{90}=Q_{0.9}\!\left(D^{\mathrm{exec}}_{q'}\right),
\]
the successor frontier element becomes
\[
\left(\pi',h\mathbin{\|}x,q',a_{50}+e_{50},s_a^2+(e_{90}-e_{50})^2,d+1\right).
\]
The search expands the highest-probability frontier first and retains at most the three most likely successors of each frontier element. It prunes a path when its probability falls below $p_{\min}=0.02$, median arrival exceeds the $120$-second planning horizon, depth exceeds eight, or the search has expanded 64 frontier elements. When multiple paths reach the same callsite $x$, their path probabilities are accumulated and capped at one,
\[
p_x=\min\left(1,\sum_{\varrho:\varrho\leadsto x}P(\varrho)\right),
\]
while the earliest predicted arrival pair is retained for scheduling that callsite.

\subsubsection{Prediction-guided KV Management}
\sysname performs proactive KV cache scheduling guided by heterogeneity and prediction. KV cache management involves deadline-driven KV promotion and prediction-aware eviction.

\paragraph{Deadline-driven KV promotion}
Deadline-driven KV promotion anticipates the incoming prompt before it arrives, using the value-flow rules obtained in Section~\ref{subsec:Discovering Heterogeneity}. Constants are inserted directly; copied values and values taken from earlier bindings and responses are resolved from the current session; and an extended value contributes the known prefix of its accumulated representation. This reconstruction proceeds binding by binding and stops at the first unresolved binding. For every predicted call, \sysname chooses the longest cache target and uses the statically known callsite prefix as a conservative fallback.

After selecting the promotion target, \sysname assigns it an estimated deadline. For a predicted call $c=(x,p_x,t_{50,x},t_{90,x})$ and timing anchor $a$, \sysname assigns the deadline
\[
d_c=\max\left(t_{\mathrm{now}},a+t_{50,x}-\kappa(t_{90,x}-t_{50,x})\right),\qquad\kappa=0.5.
\]
The term $\kappa(t_{90}-t_{50})$ moves uncertain jobs earlier and lets the scheduler prepare the prefix more conservatively.

The absolute pessimistic arrival time $\bar t_c= \max(d_c,a+t_{90})$ is used for garbage collection. If the predicted call has not arrived after $\bar t_c$, its cache-plan entry is considered stale and discarded.

Let $U_c$ be the number of target-prefix tokens absent from both cache tiers, let $H_c$ be the number resident in host memory but absent from device memory, and let $R_{\mathrm{prefill}}$ and $R_{\mathrm{promote}}$ be the profiled prefill-under-load and host-to-device transfer rates. The latest safe preparation time is estimated as
\[
r_c=d_c-\frac{U_c}{R_{\mathrm{prefill}}}-\frac{H_c}{R_{\mathrm{promote}}}.
\]
A promotion job becomes eligible whenever the engine is idle or the current time approaches $r_c$. Among eligible jobs, the scheduler selects the earliest deadline. During promotion, active KV cache and ongoing tasks are protected to ensure that speculative preparation does not interfere with serving requests.

\paragraph{Prediction-aware eviction}
\sysname exploits both predicted usage and prompt heterogeneity in KV eviction scheduling. Device-resident radix nodes are divided into four lifecycle-aware priority bands, listed in order of eviction priority:
\begin{enumerate}
\item \emph{retired}: private tail nodes belonging to completed sessions;
\item \emph{transient}: non-reconstructible prompt tails and generated descendants that are unlikely to be reused;
\item \emph{unclassified}: ordinary cache not covered by the current plan;
\item \emph{planned}: nodes required by one or more active predictions.
\end{enumerate}
The scheduler uses LRU order within the \emph{retired}, \emph{transient}, and \emph{unclassified} bands. Nodes in the \emph{planned} band are sorted by aggregated protection score and then by recency.

Band transitions occur at three events. After a request completes, nodes beyond its longest pre-arrival reconstructible prefix are marked \emph{transient}. When the session terminates, its \emph{transient} tails become \emph{retired}. At every plan refresh, \sysname removes the previous planned protections before applying the new scores, preventing stale predictions from retaining priority. 

The host tier then serves as a recovery layer. It evicts retired entries first and otherwise follows LRU. A prediction error is therefore less likely to turn into a full recomputation.

\begin{algorithm}[h]
\caption{Prediction-aware eviction}
\label{alg:eviction}
\begin{algorithmic}[1]
\Require Cache tier $\mathcal{C}$, required free space $M$,
         live predictions $\mathcal{P}$, current time $t$
\Require Lifecycle labels updated on request completion
         and session termination
\Ensure Whether at least $M$ free space is available
\While{$\textsc{FreeSpace}(\mathcal{C}) < M$}
    \State $E \gets \textsc{EvictableLeaves}(\mathcal{C})$
        \Comment{Exclude locked nodes}
    \If{$E = \emptyset$}
        \State \Return \textbf{false}
    \EndIf
    \ForAll{$v \in E$}
        \State $s_v \gets 0$
        \If{$v$ is retired}
            \State $b_v \gets 0$
        \ElsIf{$v$ is transient}
            \State $b_v \gets 1$
        \Else
            \State $b_v \gets 2$
                \Comment{Unclassified}
        \EndIf
        \If{$\mathcal{C}$ is the device tier}
            \State $\mathcal{P}_v \gets
                \{c \in \mathcal{P} : v \in \textsc{Path}(c)\}$
            \If{$\mathcal{P}_v \neq \emptyset$}
                \State $b_v \gets 3$ \Comment{Planned}
                \State $s_v \gets
                    \sum_{c \in \mathcal{P}_v} S_c(t)$
            \EndIf
        \Else
            \State $b_v \gets \min(b_v,1)$
                \Comment{Host: retired first, then LRU}
        \EndIf
        \State $K_v \gets
            (b_v,s_v,\textsc{LastAccess}(v))$
    \EndFor
    \State $v^* \gets \arg\min_{v \in E} K_v$
        \Comment{Lexicographic order}
    \State $\textsc{Evict}(\mathcal{C},v^*)$
\EndWhile
\State \Return \textbf{true}
\end{algorithmic}
\end{algorithm}

Additionally, \sysname converts every live prediction into an eviction-protection score:
\[
S_c(t)=p_x\exp\left(-\frac{\max(0,d_c-t)}{\tau}\right),\qquad\tau=60\text{ s}.
\]
This score is added to the eviction priority of every radix-tree node on the prefix's path. Nodes in the \emph{planned} band are evicted in increasing order of accumulated score, then by LRU.
