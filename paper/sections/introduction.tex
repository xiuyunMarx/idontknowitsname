\section{Introduction}

Agent frameworks increasingly expose LLM calls as programming abstractions rather than manual prompt construction. Systems such as ByLLM~\cite{dantanarayana2025mtp}, NVIDIA Object-Oriented Agents (NOOA)~\cite{furgale2026nooa}, and DSPy~\cite{khattab2024dspy} allow developers to describe model behavior using functions, objects, signatures, and modules, which framework runtimes lower into concrete prompts. This approach also appears in systems such as SIGIL~\cite{dantanarayana2026sigil}, which compiles natural-language skill documents into programs containing typed LLM calls. LLM requests from these frameworks are generated programmatically: they are the serializations of program state rather than free text. 

We observed that these programmatically generated LLM requests are inherently heterogeneous. The heterogeneity arises from three dimensions:
\begin{enumerate*}[label=(\textbf{\arabic*})]
    \item Sharing scope: one value can be shared across multiple invocations, or only within a single invocation.
    \item Lifetime: Different bindings have different lifetimes. Some bindings are single-shot volatile inputs, while others may be reuse across the whole session.
    \item Evolution pattern: context for LLM calls can evolve differently overtime, such as
  remaining fixed, being replaced, or accumulating across invocations. 
\end{enumerate*}
Figure ~\ref{fig:heterogeneity-sample} illustrates this heterogeneity in a HoVer-style \cite{jiang2020hover} fact check agent. The claim persists throughout a verification  session, the evidence list accumulates over time, and each search result is consumed once and replaced. Although these values appear in the same model invocation, they offer substantially different reuse opportunities.

This distinction matters because main-stream KV-cache serving backbones are prefix-based. In the
example, placing the accumulating \texttt{evidences} binding after the short-lived \texttt{search\_results} binding prevents the model from reusing the evidence prefix whenever the search result changes. The model must therefore recompute KV states for tokens whose contents remain unchanged. Moreover, without knowing which components persist or evolve, the serving system cannot accurately determine which cached tokens should be retained, evicted, or prefetched.

However, existing agent serving systems primarily optimize at the level of requests or agent invocation sequences. Pythia~\cite{yu2026pythia} profiles agent workflows to guide cache management, request scheduling, and autoscaling. CacheScout~\cite{zhang2026cachescout} learns execution transitions online to guide eviction and prefetching, while PBKV~\cite{zheng2026pbkv} predicts future invocations and estimates the reuse potential of cached requests. These systems exploit predictability between invocations, but treat the contents of each prompt as an opaque token sequence. Consequently, they cannot identify the heterogeneity within a single prompt, leading to a suboptimal serving performance for such program-itegrated agents.

To close the gap, we present \sysname, a compiler-serving co-design that recovers and exploits prompt heterogeneity for efficient KV-cache management. \sysname achieves this by exposing additional prefix reuse and keeping the resulting KV states resident when they are likely to be needed. The identification and exploitation of prompt heterogeneity introduces the following two challenges:

\textbf{First, heterogeneity is not always explicit in prompt.} The sharing scope and lifetime of bindings are closely bonded with the program-level structure and actual runtime assignment. Determining which layout best serves prefix caching is therefore not trivial. \sysname combines static analysis with runtime information to determine prompt layouts. The compiler derives a partial order over prompt components based on their sharing scopes and lifetimes. Then, \sysname uses the actual token lengths of bindings observed from log to order components left unconstrained by this partial order, producing a concrete layout that improves prefix cache efficiency.

\textbf{Second, exploiting future reuse requires coordinating cache retention and prefetching.}
Prompt components differ in when they will be reused and how much recomputation their cached prefixes can avoid. Retaining these prefixes consumes capacity needed by other requests, while prefetching too early occupies device memory and prefetching too late fails to hide transfer latency. Inappropriate KV-cache eviction would would lead to unnecessary recomputation. \sysname addresses this challenge through two coordinated planners: a protection planner prioritizes cached prefixes according to their expected reuse and benefit, while a prefetch planner schedules transfers based on predicted invocation deadlines and available device memory.
